After it, you should be able to predict where a new window lands, and how `move`, `join-with` and `layout` reshape the tree, _before_ you press the key.

[#notation]
== Notation

This tutorial writes trees compactly:

* `h[1 v[2 3]]` is an `h_tiles` root container that contains window 1, followed by a `v_tiles` container with windows 2 and 3
* Upper case (`H[...]`, `V[...]`) means accordion

The same tree in the xref:commands.adoc[commands reference] notation:

----
h_tiles
├── window 1
└── v_tiles
    ├── window 2 (focused)
    └── window 3
----

[#new-windows]
== Where new windows land

[IMPORTANT]
====
A new window is inserted into the _same container_ as the _most recently focused_ window, _directly after it_.
====

That's the whole rule.
(`unbindAndGetBindingDataForNewTilingWindow` in `Sources/AppBundle/tree/MacWindow.swift`)
Three consequences follow:

. *Focus first, then open.*
Focus picks both the container and the slot.
. *A new window never creates a container.*
It only joins a container that already exists.
Nesting always comes from a command such as <<join-with,`join-with`>> or <<move,`move`>>.
. *Floating windows.*
If the most recently focused window is floating, it has no tiling parent to join.
The new window is appended to the end of the root container.

The new window uses the orientation of its container.
In an `h_...` container it appears to the right of the focused window, in a `v_...` container it appears below.
xref:guide.adoc#normalization[Normalization] keeps the tree tidy: containers with one child are flattened, and nested containers alternate orientation.

[#reshaping]
== Reshaping with `move` and `join-with`

* xref:commands.adoc#join-with[`join-with <direction>`] _creates_ nesting.
It wraps the focused window and its neighbour into a new container.
* xref:commands.adoc#move[`move <direction>`] _relocates_ the focused window.
Nesting disappears on its own when a container is left with one child (flatten normalization).

New windows never create containers.
So these two commands (plus xref:commands.adoc#layout[`layout`]) are how every nested layout is built.

[#join-with]
=== `join-with`: wrap me and my neighbour

[IMPORTANT]
====
Take the focused window and the _nearest node_ in the direction.
Put both into a _new container_ with the _opposite orientation_ of their parent, at the neighbour's old place.
====

* `join-with right` / `join-with down`: the focused window ends up *first* (left or top) in the new container.
* `join-with left` / `join-with up`: the focused window ends up *last*.
* The neighbour can be a whole container.
Then the new container holds the focused window plus that entire subtree, which can rotate things you didn't expect (see the quiz).

++++

[#move]
=== `move`: three cases

Look at the parent of the focused window.
Does it have the orientation of the move (horizontal for `left`/`right`, vertical for `up`/`down`), and is there a sibling in that direction?

[cols="1,2,2"]
|===
|Situation |Result |Example

|*1. Swap.* The sibling is a window.
|The two windows trade places.
|`h[1 2 3]`, 2 focused, `move right` → `h[1 3 2]`

|*2. Move in.* The sibling is a container.
|The window dives into the container and lands after its _most recently focused_ window (the new-window rule again).
|`h[1 2 v[3 4]]`, 2 focused, `move right` → `h[1 v[3 2 4]]` if 3 was focused more recently than 4

|*3. Move out.* The parent has the wrong orientation, or there is no sibling in that direction.
|Climb up until an ancestor has the right orientation. Land right beside the container you climbed out of.
|`h[1 v[2 3]]`, 3 focused, `move left` → `h[1 3 2]`
|===

[IMPORTANT]
.The workspace edge
====
If the move out climbs all the way to the root container, AeroSpace wraps the _entire old tree_ in a new root container with the orientation of the move, and puts the window beside it.

`h[1 2 3]`, 3 focused, `move down` → `v[h[1 2] 3]`: window 3 spans the full width at the bottom.
====

This is `--boundaries-action create-implicit-container`, the default.
It also explains why `move right` on the rightmost window of `h[1 2 3]` doesn't do nothing: it gives `h[v[1 2] 3]`.

[#layouts]
== Layouts: tiles, accordion, orientation

Windows don't have a layout.
Every _container_ has two independent properties, a layout and an orientation (see xref:guide.adoc#layouts[Layouts]):

[cols="1,2,2"]
|===
| |`horizontal` |`vertical`

|`tiles`
|`h[...]` side by side
|`v[...]` stacked

|`accordion`
|`H[...]` one window visible, the others peek out left and right
|`V[...]` one window visible, the others peek out at the top and bottom
|===

xref:commands.adoc#layout[`layout`] changes the _parent container of the focused window_.
Just like for new windows, focus picks the target.

In an accordion, the most recently focused window fills the container.
The other windows are stacked behind it, their edges visible as `accordion-padding`.
`focus` in the direction of the accordion cycles through them.

[#layout-keys]
=== `alt-slash` and `alt-comma`

The xref:guide.adoc#default-config[default config] binds:

[source,toml]
----
alt-slash = 'layout tiles horizontal vertical'
alt-comma = 'layout accordion horizontal vertical'
----

[IMPORTANT]
====
Walk the arguments left to right, and apply the _first one that doesn't already describe_ the container.
`tiles` and `accordion` keep the orientation.
`horizontal` and `vertical` keep the layout.
====

So each key toggles in two steps:

[cols="1,2,2"]
|===
|Container is |`alt-slash` |`alt-comma`

|`h` tiles |→ `v` (flip) |→ `H` (to accordion)
|`v` tiles |→ `h` (flip) |→ `V` (to accordion)
|`H` accordion |→ `h` (to tiles) |→ `V` (flip)
|`V` accordion |→ `v` (to tiles) |→ `H` (flip)
|===

In short: if the layout is wrong, switch the layout; if the layout is right, flip the orientation.

[#layout-flip]
=== Flipping the orientation rotates the ancestors

[IMPORTANT]
====
With `enable-normalization-opposite-orientation-for-nested-containers` (the default), flipping the orientation of a nested container also flips _every ancestor_, alternating up to the root container.
Nested containers must stay opposite to their parent.
====

In `h[1 v[2 3]]` with window 2 focused, `alt-slash` doesn't put 2 and 3 side by side on the right.
It gives `v[1 h[2 3]]`: 1 on top, 2 and 3 below.
The whole workspace rotates by 90°.
(`changeOrientation` in `Sources/AppBundle/tree/TilingContainer.swift`)

++++

* Switching between `tiles` and `accordion` never touches the ancestors.
Only orientation flips propagate.
* To get 2 and 3 side by side on the right, un-nest them: that's `h[1 2 3]`.
Use `move`, not `layout`.

A typical use of an accordion is one slot for several windows that you look at one at a time.
For example, `h[1 V[2 3 4]]`: an editor on the left, and a browser, a terminal and docs on the right that you cycle with `alt-j` / `alt-k`.
Build the nesting first (<<reshaping>>), focus a window inside it, then press `alt-comma`.

[#monitors]
== Two monitors

See also xref:guide.adoc#multiple-monitors[Multiple monitors] in the guide.

* All monitors share *one pool* of workspaces.
Each monitor shows exactly one of them, its _visible_ workspace.
Two monitors can't show the same workspace.
* Every workspace, even an invisible or an empty one, *belongs to a monitor*.
* Monitors are numbered from left to right, starting at 1.
`main` is the monitor set as the main display in `System Settings -> Displays`.

[IMPORTANT]
.Which monitor does a workspace belong to?
====
The first of:

. its xref:guide.adoc#assign-workspaces-to-monitors[forced assignment] from the config
. the monitor it's _visible_ on
. the monitor it was _last shown_ on
. the `main` monitor
====

(`workspaceMonitor` in `Sources/AppBundle/tree/Workspace.swift`)
Step 3 is easy to forget: a workspace remembers where it was last shown.

[#monitors-workspace]
=== `workspace X`

* *X is visible:* nothing moves, only the focus jumps to the monitor that shows X.
* *X is invisible:* X replaces the workspace that its monitor shows, and the focus jumps there.
This happens even if you were working on the other monitor.
* *X doesn't exist yet:* it belongs to the `main` monitor.
Unlike i3, AeroSpace doesn't open it on the monitor you're looking at.

[NOTE]
====
An empty, invisible workspace is destroyed, unless it's listed in `persistent-workspaces`.
It forgets the monitor it was shown on.
When you switch to it again, it's a new workspace, and it appears on the `main` monitor.
====

[#monitors-move]
=== Moving windows and workspaces

[cols="1,1,2"]
|===
|To |Command |What happens

|move the focused *window* to the other monitor
|xref:commands.adoc#move-node-to-monitor[`move-node-to-monitor next`]
|The window joins the root container of the workspace visible there.
With `right` or `down` into a root of the same orientation, it lands *first*, on the side it came from.
Otherwise, it lands *last*.
The focus stays behind unless you add `--focus-follows-window`.

|move the focused *workspace* to the other monitor
|xref:commands.adoc#move-workspace-to-monitor[`move-workspace-to-monitor --wrap-around next`] (`alt-shift-tab` in the default config)
|The workspace moves and stays focused.
The monitor it left shows another workspace instead.
Fails for workspaces with a forced assignment.

|bring *workspace X* to the focused monitor
|xref:commands.adoc#summon-workspace[`summon-workspace X`]
|X appears on the focused monitor, wherever it was before.
From now on, X belongs to this monitor (step 3).
|===

"Another workspace instead" means: the workspace that the monitor showed before, or any invisible workspace that belongs to the monitor, or the first empty workspace with a numeric name (`1`, `2`, ...).
(`getStubWorkspace` in `Sources/AppBundle/tree/Workspace.swift`)

[#monitors-focus]
=== Focus across monitors

`alt-h` / `alt-l` in the default config are `focus left` / `focus right`.
The default is `--boundaries workspace`, so the focus *stops* at the edge of the monitor.

* `focus --boundaries all-monitors-outer-frame right` continues onto the next monitor.
It focuses the _most recently focused_ window of that monitor's workspace, not the geometrically closest one.
* `move` has the same flag.
At the edge, the window goes to the other monitor, like `move-node-to-monitor` with the focus following it.
But then the inner monitor edge no longer creates an implicit container (see <<move,the workspace edge>>).

[#monitors-try]
=== Try it for real

----
aerospace list-monitors
aerospace list-workspaces --all --format '%{workspace} %{monitor-name} %{workspace-is-visible}'
----

. Run the `list-workspaces` command.
Predict the monitor column before you read it.
. Focus the secondary monitor, then switch to workspace 1 (`alt-1`).
Where does 1 appear, and where is the focus?
. On workspace 1, press `alt-shift-tab`.
Predict what the main monitor shows now.
Run `list-workspaces` again: which monitor does 1 belong to now?
. Open two windows on the main monitor and run `aerospace move-node-to-monitor --focus-follows-window next`.
Predict whether the window lands on the left or the right.
. Focus the rightmost window on the main monitor and press `alt-l`.
Then try `aerospace focus --boundaries all-monitors-outer-frame right`.
